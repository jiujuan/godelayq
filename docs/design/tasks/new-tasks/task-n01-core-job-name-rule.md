# TASK-N01　任务名称规则（core）

- 所属阶段：M0 语义
- 依赖任务：无
- 涉及文件：`core/job_name.go`（新增）、`core/job_name_test.go`（新增）、必要时 `core/job.go` 的字段注释
- 预计规模：小

## 1. 任务目标

在 `core` 里交付一条唯一的服务端名称规则：`core.ValidateJobName(name string) error`，
判定"中文、字母、数字，1..64 个字符，其它字符一律拒绝"。
本卡结束时这个函数可用、有完整用例，但**还没有任何调用点**——接线在 TASK-N02。

## 2. 背景与当前问题

任务名称现在是注册表的键，因此它只能长成键的样子（`payment_check`、`exec.demo-run`），
使用者无法起一个"每晚对账"这样的名字（需求①）。改造后名称退化成给人看的标签，
就需要一条标签规则：既要允许中文，又不能让任意字符串进来——它会出现在列表页、
任务详情标题、事件时间线、日志与 `ErrorResponse.Details` 里。

`core` 已经有三条同类规则可以先例照抄：

| 先例 | 位置 | 抄什么 |
| --- | --- | --- |
| 档位名规则 | `core/executor_profile_store.go:22`（`^[A-Za-z0-9_-]{1,64}$`）与 `:240` `ValidateProfileName` | 长度上限、错误文本的写法（把被拒的值与允许的字符集一起说清） |
| 分组名规则 | `core.ValidateGroupName`（调用点 `api/handlers.go:26-34`） | "规则放 core、API 与前端各判一遍"的分工 |
| 名称进 URL 的理由 | `core/executor_profile_store.go:16-21` 的注释 | 每条规则都要写明"为什么这些字符不行"，注释不能只写正则 |

## 3. 要实现的功能

### 3.1 函数

```go
// ValidateJobName 校验任务名称（给人看的标签）。
// 允许：汉字、英文字母、数字；长度 1..64 个字符。
func ValidateJobName(name string) error
```

放在新文件 `core/job_name.go`，不进 `core/job.go`（那份已经 300 多行，且规则与
`Job` 结构本身没有依赖关系）。

### 3.2 判据（逐条都要有用例）

1. 正则：`^[\p{Han}A-Za-z0-9]{1,64}$`。用 `\p{Han}` 而不是硬编码区间（`一-鿿` 之类
   会漏扩展区的字，且需要长期维护）。
2. 长度按 `utf8.RuneCountInString` 计，不是 `len()`：65 个汉字的名称必须被拒，
   而 3 个汉字（9 字节）必须通过。
3. 空串拒绝，错误文本说"必填"。
4. 被拒的字符集要在错误文本里点名，且**只点名第一处**、不回显整个名称：
   名称里可能带内部系统的名字，而这条错误会进响应体与日志。
   拒绝清单至少覆盖：空格、制表符与换行、`_`、`-`、`.`、`/`、`\`、`:`、`@`、`%`、
   引号与尖括号、全角空格与全角标点。
5. 前后空白**不做 trim 后放行**：`" 白天巡检 "` 属于带空白的名称，按规则拒绝。
   这一点与 `core/job.go` 的 `IsExecHandlerKey`（`:23-25`）不同——那一处判的是注册键，
   它容忍空白是因为执行侧本来就会 trim；标签不需要这个容忍。
6. 哨兵值：名称等于 `exec.` 前缀开头的写法在这里**不管**（规则本身会因带点而拒掉
   `exec.php` 以外的写法，而 `execphp` 是一个合法标签）。名称与类型的一致性
   不由本函数负责，见 §8。

### 3.3 错误类型

单列一个包装变量便于调用方判"这是取值问题而不是内部错误"：

```go
var ErrJobNameInvalid = errors.New("invalid job name")
```

错误文本用 `%w` 包住它，与 `ErrProfileNameInvalid`（`core/executor_profile_store.go:25`）同一体例。

## 4. 实现步骤

1. 写 `core/job_name.go`：正则变量 + 导出的错误变量 + `ValidateJobName`。
   注释三段：允许什么、为什么这些字符不行（名称会出现在哪些地方）、长度按字符计。
2. 写 `core/job_name_test.go`：表驱动，通过组与拒绝组各覆盖 §3.2 的每一条，
   并单独一条断言错误文本里包含被拒的字符类别、不包含完整名称原文。
3. `gofmt -w core/job_name.go core/job_name_test.go`（本仓库 `gofmt -l` 因 CRLF 不可用）。
4. `go test ./core -run JobName`，再 `go build ./... && go vet ./...`。

## 5. 测试要求

- 单元：§3.2 六条逐条。通过组至少含纯中文、纯小写字母、纯数字、三者混合、64 个汉字；
  拒绝组至少含 65 个字符、空串、空格、`_`、`-`、`.`、`/`、`\`、`@`、`%`、`<script>`、
  全角空格、换行、以及"前后带空白的合法字符组合"。
- 一条按字符计数的用例：3 个汉字通过、65 个汉字拒绝，并在断言消息里写明"按字节会误判"。
- 一条错误文本用例：`strings.Contains(err, "中文")` 这类稳定片段可断言，
  但**不要**断言整个句子原文（后续卡会调措辞）。
- 全仓回归：`go test ./core`。本卡没有调用点，因此其它包必然零变化，不必跑全仓 `-race`。

## 6. 完成标准（DoD）

1. `core.ValidateJobName` 存在且只有一份实现（`grep -rn "jobNamePattern" core` 只命中新文件）。
2. §3.2 六条判据逐条有对应用例，用例名或表项能看出对应哪一条。
3. 错误值能被 `errors.Is(err, core.ErrJobNameInvalid)` 判出来，用例断言过。
4. 没有任何调用点被改动：`git diff --stat` 只含两个新文件。
5. `go build ./...`、`go vet ./...`、`go test ./core` 全绿。
